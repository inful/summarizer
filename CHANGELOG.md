# Changelog

All notable changes to summarizer are documented here. The format is
based on [Keep a Changelog](https://keepachangelog.com/), and this
project adheres to [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Changed
- **`runCmd` had no test at all.** 171 lines, and the only function in `cmd/summarizer` with no coverage — every sibling (`resolveLLM`, `newGuard`, `newPublisher`, `printSummary`, `classify`, `unionSlices`, `stringSliceFlag`) is called from one, while the package sat at 40.0%, the lowest in the repo by a factor of two. It is where flag-vs-config precedence, the discovery default and the six-stage wiring live, and none of it needs a network to test: a missing token, a bad config key, an unknown flag and a publish block with no project all resolve before a client is constructed. Eight cases now pin the exit codes a cron wrapper branches on — 2, 3 and 7 — and two of them pin the *different* codes for the two ways `publish.enabled: true` can be misconfigured. 40.0% → 61.6%.
- **The `Publisher` contract promised concurrency-safety it did not have, and named the refactor that would break it.** The interface said *"expected to be safe to call concurrently"*, and the parenthetical said *"the per-audience LLM-then-write pairs could run in parallel in the future"*. The per-branch memo is correctly guarded — mutex on all three accessors, a value copy out of `recalled`, a non-destructive merge in `remember` — but `findOrCreateMR` is a check-then-act across two network calls, and the mutex covers the memo rather than the sequence. Two concurrent publishes for one period would each POST a merge request; GitLab permits multiple open MRs from one source branch, so nothing rejects the second. `run.Pipeline` has the same exposure from the other direction: `lastActiveEpics`, `groupEpics` and `lastExcluded` are three maps with no mutex at all. The contract now says what is true — safe across *different* periods, single-writer per period — and names what to add before parallelising either loop. `TestGitLabPublisher_ConcurrentPublishAcrossBranchesIsRaceFree` pins the half that does hold under `-race`; it reports three data races if `remember`'s mutex is removed, so it tests the publisher rather than the fixture.
- **`fakeGitLab` answered a merge-request query with every branch's MRs.** It filtered on `?state=` but not `?source_branch=`, which the publisher has always sent. Sequential tests never saw it — nothing else had created an MR yet — but six goroutines across six periods produced *five* merge requests, because a goroutine asking about its own branch found another branch's open MR, concluded one existed, and returned its URL. The concurrency test failed about one run in three for two rounds before the cause was found. Both filters are applied now, as GitLab does.
- **`fakeGitLab` was not safe for the concurrent test it needed to host.** `lastMRDesc`, `flakyMRCreates` and `mergeRequests` were plain struct fields while the counters beside them were atomics. Six goroutines through the handler tripped the race detector on the fixture — a test that can only fail for the wrong reason is worse than none. Now mutex-guarded.
- **`getAll`'s truncation flag is read by one caller of six.** `FetchActiveProjects` uses it and logs that the scan stopped early; `FetchMRs`, `FetchIssues`, `FetchCommits`, `FetchEpicIssues` and `FetchEpics` all discard it with `_`. That is not an oversight — the five page a single project or group and stop at `maxEventPages`, whose `shortcut:` marker names the limit and explains that the pages dropped are the oldest, i.e. the ones `capEvents` would cut anyway. No behaviour change; the doc now says which caller reads the bool, which five do not, and why, so it is neither deleted by a future reader nor used where the decision has already been made.
- **`admitUpTo`'s budget has a cost ceiling nothing stated.** The budget counts inclusions rather than candidates, deliberately, so a quiet instance publishes nothing rather than claiming a cap worked. The consequence was undocumented: `admit` is ~6 sequential round-trips and `maxActiveScanPages` bounds the candidate list at 1,000, so an instance where nothing is includable walks all of them — roughly 6,000 requests for a run that publishes nothing. A `shortcut:` marker now names the bound.
- **Reports no longer carry a title of their own in the body.** The frontmatter `title` is the one docbuilder renders, so a leading `# Weekly engineering update` in the Markdown is a visible duplicate of it. All eight prompts now tell the model not to write a line starting with `#`, and `stripLeadingTitle` removes one if it does — in `NewFrontmatter` before the fingerprint is computed, and again in `Render` where the file's bytes are assembled, because `Publish` passes `Render` the original body and stripping in one place only left the H1 in the document and out of the hash. Only one H1 and only at the very start: `## Highlights` further down is content, and `#notaheading` is not a heading in Markdown at all. A body with no leading H1 is returned byte-for-byte, so existing documents keep their fingerprints. The local-disk publisher is deliberately untouched — it writes no frontmatter, so there the H1 is the only title the file has.

### Fixed
- **The run summary printed rollup token usage that nothing ever recorded.** `Result.TokensByAudience` — commented *"rollup token usage, when applicable"* — was declared, initialised at the top of `Run` and looped over by `printSummary`, with **no code path writing it**. `runAudienceRollups` took `resp.Usage` from every rollup completion and dropped it on the floor, so the field was always empty and the `tokens[rollup/…]` line could never fire. The cost of that is not cosmetic: `--max-events`' own help says *"each project costs two completions, so this bounds the per-run bill"*, and the combined rollup, the epic rollup and `summarizer monthly` all make LLM calls whose tokens appeared nowhere. Both rollup paths now accumulate into the field, keyed `"<kind>/<audience>"` so the epic rollup cannot overwrite the combined one, and the per-key summary lines go through a sort so two runs over identical input print identically.
- **Confidential issue and epic titles reached documents published `public: true`.** GitLab's `confidential` flag — the owner's own "not for everyone" — is set on issues as well as epics, and a `read_api` PAT owned by a project member receives both from the ordinary list endpoints. Executed against `prompt.Render`: `customer confidential EPIC title in prompt: true`, `customer confidential ISSUE title in prompt: true`. So an issue titled "ACME pricing renegotiation — INTERNAL ONLY" was summarised into a file anyone could read, and `writeEventLine` said so about itself — *"the title reaches a customer-facing document"* — while reading a field `gitlab.Issue` did not have. The customer epic **rollup** was already guarded (`bucketEpicsByCustomer`: *"this audience's files are published `public: true`, so it cannot go here whatever its labels say"*), but `Render` is the other path that renders epics and it had no guard; the cross-project rollup consumes the rendered text and inherited the leak. `gitlab.Issue` now carries `Confidential`, and `prompt.forAudience` drops — for the customer audience only — any confidential event, any event inside a confidential epic, and that epic's heading. The second is not redundant: a confidential epic's child issues are ordinary issues. Team output is untouched, and the filter runs before `capEvents` so a confidential item cannot take a budget slot and displace an ordinary one.
- **`summarizer monthly`'s reads had no retry at all, not even on a 502.** `getStatus` built its own request rather than going through `doRetry`, so `ListPeriodBranches` and `ReadReportFile` inherited none of its policy — measured at `attempts=1` for both a 502 and a dropped connection against a server that recovered on attempt two. One connection reset aborted the command outright, on a subcommand that runs on the 1st, so a failure costs a month. `getStatus` is now four lines over `doRetry`, which gained a headers return (what it needed for `X-Next-Page`; `api` is its one other caller and discards them). Transport failures are retried **for GET only** — a GET has no side effect to duplicate, a POST or PUT may have landed and still look like a failure, which is what keeps the merge-request create from opening two MRs. The audit that prompted this was itself a repeat: the same defect was fixed in `internal/gitlab` one round earlier, in the copy one package over.
- **`ListPeriodBranches`' comment claimed a narrowness it only had when a prefix was configured** — but writing the test showed the exposure was smaller than the audit assumed, because `isWeekSlug` tests the *whole* branch name and requires 8 characters, so `other-tool/2026-W41` is excluded on length either way. An unset prefix only claims a branch named exactly `YYYY-Wnn`, which is what `PeriodBranch` produces in that configuration. Both configurations are now pinned by test.
- **An ambiguous branch-create retry lost the whole week and named the wrong cause.** The publisher's retry comment claimed branch create was "guarded by `branchExists` … so both are safe to repeat" — but `branchExists` guards the *pre-check*, not the retry. When a proxy or a GitLab pod restart turns a successful 201 into a 502, the retry lands, GitLab answers 400 `"has already been taken"`, and `ensureBranch` returns a hard error **for a branch that exists**. The run aborted with every write actually having succeeded, and the memo was never set, so every subsequent file in the period paid the same failing POST. `ensureBranch` now re-checks on the failure path and treats "it is there now" as success — one extra GET, only when the POST failed. The file write was always safe (`last_commit_id` makes the PUT idempotent) and the MR create is still not retried; the comment now says which is which instead of collapsing all three into "safe to repeat".
- **A dropped connection cost one project's entire week while a 502 from the same event retried three times.** `doJSON` returned on `c.http.Do` error with no second attempt, though its 429 and 5xx branches both retried. Measured against the same server recovering on its second attempt: **502 → `attempts=2 err=<nil>`; connection reset → `attempts=1 err=connection reset by peer`**. A GitLab pod restarting mid-scan drops in-flight connections, which is the ordinary way this arrives. `doJSON` is GET-only (`http.MethodGet` is hardcoded), so there is no write to duplicate and retrying is unconditionally safe. `internal/publisher`'s `doRetry` deliberately still does not — its POSTs can land and still look like a failure. The loop had no test at all, which is how the gap survived while `internal/llm`'s identical loop got it right; `sleepFn` added following the publisher's pattern so the retry path runs in microseconds rather than 7 seconds of real backoff.
- **`--include-diffs` was documented in three places as adding one API call per MR. It adds none.** `fillMRDetail` calls `FetchMRDetail` for every merge request unconditionally — `wantDiffs` only decides whether the chunks are *kept* — because `prompt.Render` needs the `+N/-M in K files` aggregate either way. The claim appeared in the flag help, the README caps table and the README prose, while the code comment above `fillMRDetail` and this changelog both said the opposite: *"every run paid the full cost … and threw the text away."* The cost is not small — measured against a 25-project fleet with 20 MRs each, **676 requests of which 500 were `/changes`, 74%**, one per MR. So the run's largest wire cost had a flag that appeared to control it and did not. `TestIncludeDiffsFlagHelpDoesNotClaimAnAPICall` pins the help string.
- **`backoff` clamped one value twice, with the second clamp unreachable.** `if mult > 30 { mult = 30 }` followed by `if d > maxBackoff { d = maxBackoff }` — both bounds 30, so the second could never fire. Now one `min`, matching `internal/llm` and `internal/publisher`. The comment also states what the pair obscured: the cap is the **base**, not the ceiling, because jitter is added after it.
- **`textutil.Truncate` allocated 4× its input on six error paths.** It returned early when the string fit the cap, which is what made it look allocation-free; when it did not fit it fell back to `[]rune(s)` — four bytes per byte for the whole input. Six call sites pass an entire HTTP response body, bounded at 16 MB, through a 200- or 300-character truncation: `internal/gitlab/client.go`, `internal/publisher/gitlab.go`, `internal/publisher/monthly.go`, `internal/llm/openai.go`. Measured: **64 MB allocated to produce a 203-byte string**, on an error path, where memory is already under pressure. Now built rune by rune — **4.000× → 0.000×**, byte-identical including the invalid-UTF-8 normalisation that `[]rune` provided, pinned by `TestTruncate_MatchesTheRuneSliceByteForByte` across 72 input/cap combinations. This was the same bug `cappedDiff.UnmarshalJSON` had in round 18, fifty lines away, with the fix and a comment explaining the trap already written there.
- **The release workflow ran the weaker test gate on the code most likely to need the stronger one.** `release.yml` ran `go test` without `-race` while `ci.yml` runs with it — inside the workflow whose own first paragraph exists for "a tag pushed from a branch whose CI never went green, or from a machine with no hooks at all." Now identical to CI, which is the same ~10s CI already spends inside a 30-minute job budget.
- **The frontmatter contract documented five document shapes; the code produces six.** A per-customer epic rollup is `KindRollup` with `Project` carrying the `org::` code — the round-16 change that stopped two customers' `public: true` documents sharing a title — and no row in `docs/frontmatter-schema.md` described it, in the title table or the tags table, where the customer code becomes a tag and is the only thing telling those documents apart in a docbuilder index. Nothing caught it: `docbuilder-lint` validates that file and **skips silently** when the binary is missing or broken, which a bare mise shim with no pinned version is — `docbuilder --version` returns `mise ERROR No version is set for shim: docbuilder` — and `lefthook.yml` says so itself. Knowing a control does not run is not compensating for it. Both tables now have the row, and `TestNewFrontmatter_EveryTitleShapeIsInTheSchemaDoc` renders one `Frontmatter` per shape and asserts each title appears in the doc, so neither a new shape nor a deleted row passes quietly.
- **`examples/summarizer.yaml` had no `internal_only_projects` — the one config key with no example.** The file operators copy demonstrated four keys live and two opt-in blocks commented out (`publish:`, `safety:`); every key the struct binds appeared except the audience override, which is the switch for suppressing customer-facing output for a project whose documents are published `public: true`. It was documented in the README and the runbook, but the example is where an operator looks for what can be turned on, and it showed two of the three. The block now documents the case-insensitive matching and the trimming alongside the key — the normalisation that failed open twice, in rounds 19 and 21.
- **The quickstart promised `publish.project` never summarises itself.** It does not: `PublishTarget` is checked in exactly one place, inside the discovery closure, and an explicit `--project` overrides it deliberately — the code says so at the check, `TestResolveProjects_ExplicitPublishTargetStillRuns` pins it, and `docs/how-it-works.md` states it correctly. The quickstart was the one document out of three claiming the opposite, and an operator who believed it had no reason to exclude the target from their own `--project` list — which produces a weekly report describing summarizer's own reports. Unlike most stale-comment findings this one *overstated* a guarantee rather than understating a capability; `deferred.md` carried the same claim without its caveat and is corrected too.
- **The quickstart's example run summary predated round 15.** It showed `window=this ISO week (since Monday 00:00 UTC, 60h0m0s elapsed)` — the format from *before* the change that added the window's dates, which exists precisely because a Monday cron prints a correct-looking three-day range covering three hours. Replaced with output captured verbatim from `printSummary`. The prose also said "one-line run summary" above a five-line example.
- **`docs/deferred.md` D1 listed a flag that ships.** Its missing piece was "a `--group` flag mirroring `--project`"; that is `--discover-group`, which exists and is documented two rows below in the same table. Only the `groups:` config key is genuinely absent, and the entry now says so.
- **The caps table in the README said "runes" for two budgets the code measures in bytes.** `rollupTotalCap` and `diffMaxPerMR` are byte counts — `sum += len(body)` and `remaining -= len(c.Diff)` — while `maxDiffRunesPerFile` and `rollupPerBodyCap` are rune counts. The table did not distinguish, so an operator sizing `--include-diffs` against their model's context did the arithmetic in the wrong unit and was wrong by up to 4× on non-ASCII diffs. This is the same byte/rune boundary that produced the invalid-UTF-8 bug: the *code* handles it correctly and says so in a comment, and the *documentation* never caught up. Every row now names its unit, and three caps the table had omitted entirely — `maxEventPages`, `maxActiveScanPages` and `maxResponseBytes`, each carrying a `shortcut:` marker — are listed too, because a unit column only forces a choice at authoring time if the table is complete.
- **`runEpicRollup`'s comment asserted `Project: ""` for all buckets; only the team one is.** Round 16 introduced `rollupPart.label` so each customer's `public: true` epic rollup gets its own title and tag set, and the comment above the function kept describing the old shape three lines away from the code that contradicts it. It now names the split: the customer code per customer bucket, `""` for the single team-wide one. The neighbouring comment quoted a document title that round 21 changed (`all subscribed projects` → `all customer-facing projects` for the customer audience) and is now marked as historical rather than presented as current.
- **`TestEpicRollup_TeamBucketCarriesNoCustomerLabel` pins the half of that claim nothing tested.** The customer half has been covered since round 16; the team half — a bucket that spans every project must name none, or `NewFrontmatter` turns it into a title reading as one project — was asserted nowhere. Giving `bucketAllEpics` a customer fails it.
- **The MR trim and the prompt cap disagreed on which merge request was newest.** `keepNewestMRs` bounds the list before paying for a `/changes` call per MR, and `prompt.capEvents` then re-sorts everything and keeps the newest `MaxEvents`. The trim's stated purpose is that *"an MR capEvents would drop anyway" must not cost a request* — which only holds if the two order identically. They did not: `keepNewestMRs` tied on numeric IID, `capEvents` ties on `Kind+Ref`, and for MRs that is `"#10" < "#9"`, the opposite order. Measured: with two MRs merged in the same second, the trim kept MR 9 and the prompt kept MR 10 — the request was spent on nothing and MR 10 rendered with no `+N/-M in K files` suffix. GitLab returns `merged_at` at second precision, so a bulk "merge all eligible" or a rebase-and-merge batch produces exactly those ties. The comment claimed *"IID is the tiebreak for both"*, which was never true. `keepNewestMRs` now uses the event `Ref`, and a test drives the pair through the real `prompt.Render` so the two cannot drift apart again.
- **The customer rollup's title claimed the whole fleet.** It is built from `eligibleProjects`, which drops every team-only project, and customer output is opt-in per project — so on a typical fleet the customer file covers a minority of the run. Measured: 3 projects in the run, 2 in the rollup, title reading "…all subscribed projects". The body header is accurate; only the docbuilder index entry overstated, and that is what a reader sees first. The team rollup sees everything and now says "all projects".
- **The template escaping test could only check fields someone remembered to list.** `.` — the single-variable form of `{{data .}}` over `.ProjectNames` — was missing from `unsafeFields`, so downgrading it to a bare `{{.}}` in `rollup-team.tmpl` passed the suite: in a template published `public: true`, where a project path containing `</data>` would close the block. `.` appeared in six places with two different proven-safety classes, so the monthly templates now name the variable (`{{range $week := .WeekNames}}`) and `.` means one thing. `safeFields` is the new half of the classification, each entry carrying its reason, and `TestTemplates_EveryFieldIsClassified` requires every interpolation to land in exactly one of the two maps. It caught the four `.` sites the moment it existed.
- **The customer epic rollup listed epics with zero activity for that customer.** `bucketEpicsByCustomer` skipped an epic on `ev.Total` and then printed `ev.ByCustomer[code]` — two different numbers, and a non-zero total says nothing about the customer whose file it is. ActiveEpics is the *group's* list, so the project may own none of the epic's issues; and even when it owns some, `codes` comes from `EpicCustomerCodes`, which reads the group-wide issue list, so one GLOBEX-tagged issue anywhere in the group opens a GLOBEX bucket from every project in it. Measured, from project `g/a` of a two-project group: `Total=1`, `ByCustomer=[ACME:1]`, `EpicCustomerCodes=[ACME GLOBEX]` — and GLOBEX's file, published `public: true`, carried "0 events" for an epic whose work was all in `g/b`. Round 16 closed this shape one field over and its test only checked the project dimension. The team bucket keeps `ev.Total`, which is correct there: internal readers want the whole fleet.
- **`Retry-After` overflowed past its cap in all three copies of the parser.** `internal/gitlab`, `internal/llm` and `internal/publisher` each had their own `retryAfter`, and all three did `time.Duration(n) * time.Second` — int64 *nanoseconds* — and capped the result afterwards. Past about 9.2 × 10⁹ that goes negative, and a negative duration means "no wait at all", the exact opposite of what the header asks for: `Retry-After: 9999999999` produced `-2346317h` and four immediate retries. `internal/gitlab`'s own comment says capping is why the code exists, and its `backoff` guards `if d < 0` ten lines away because *jitter* can make it negative. Now one `textutil.RetryAfter` that caps the seconds before multiplying, so the negative case cannot be constructed — which is what that package's doc means by "one home so a fix lands once instead of once per copy". The old test asserted `retryAfter("999999")`, eleven orders of magnitude below the boundary, which is exactly why it passed; the new table brackets it. `backoff` and `sleep` stay local: they differ on purpose.
- **The combined rollup claimed every project and carried a handful.** `capBodies` holds the rollup to `rollupTotalCap` — 16,000 bytes for the whole file, every project in it — and on a wide run most projects never make it. Measured: 20 projects at ~2 KB each carried **8 bodies and dropped 12**, while the prompt header read `Projects in this rollup: 20` and listed all 20 names. The names are deliberate (`capBodies` leaves them whole so the model can see which lost their body) but the gap is invisible to a human reading the published file, so a partial week read as a complete one. The customer rollup is the worse half: it is published `public: true`. `RenderRollup` now counts the drops and the header carries the same `(N shown, M omitted for size)` disclosure `RenderEpicRollup` has had since its own silent truncation was fixed, worded identically so the two files read alike. `RenderMonthlyRollup` has the same gap 15 lines away and is not fixed here — a month is 4–5 weeks so it rarely trips, but a five-week month at the per-body cap does drop one.
- **The window is the ISO week, and there is nothing else to set.** Reports are filed under `summarizer/2026-W43/`, and the window used to be `now - 168h`, so the two disagreed: run on a Monday and the file named `2026-W43` held nothing from week 43 and a full week of week 42. The window is now Monday 00:00 UTC to now (`run.WeekStart`), so it matches its directory by construction, and `--since` and `default_lookback` are gone rather than kept as overrides. Greenfield: a second window size would only create a class of bug where the filename, the directory and the contents disagree, and `summarizer monthly` would have to disambiguate between files that should never have coexisted.
- **The documented cron moved from Monday to Sunday 23:00 UTC.** The window is the ISO week, so a Monday run covers three hours and reports on the week that is only starting — six days summarised by nothing, with nothing in the output to say so. A Sunday 23:00 run covers 167 hours and reports on the week it is closing. Daily also works and refines each week across seven runs, at seven times the cost; a single weekly run is the intended cadence, and it is the one that loses the whole week if the machine is off at 23:00.
- **The monthly rollup's trailing partial week is dropped by default, and now says so.** A month always has one: September 2026 owns W37–W40, and W40 runs to 4 October, so a monthly run on the 1st finds no branch for it and the last three days of every month are in the weekly reports but in no monthly rollup. Running it on the 5th closes the gap and folds 1–4 October into September instead. For a customer-facing document a missing week reads better than the wrong one, so the 1st stays the documented default.
- **The run summary now prints how long the window was**, not just its dates. `this ISO week 2026-10-19 → 2026-10-21 (3h0m0s elapsed)` makes a misconfigured cron visible where the operator will see it; the date range alone looks correct either way.
- **Filenames say `wk`.** The window token used to be a day count derived from the duration, which under a week-to-date window rendered as however many whole days had elapsed — `3d` on a Thursday — so the same week's file was renamed daily and no two days agreed on what it covered.
- **A customer code's filename segment now ends in a short hash:** `org::ACME` writes `combined--epics-acme-a8308e--wk--customer.md`. `slugCustomer` lowercased the code and collapsed punctuation, which is lossy — `org::"Acme  EU"` and `org::"acme.eu"` both produced `acme-eu`, so two customer buckets wrote one document, the second overwrote the first, and `readExistingUID` then published the FIRST customer's docbuilder UID on the second's report. That file is `public: true`. It is the same failure `sanitize` had for project paths, one function over: fixing one is not the same as fixing the class. Six hex characters of SHA-256 over the original code, after the readable prefix, so the directory still browses.
- **A per-customer epic rollup now names its customer in the frontmatter.** `NewFrontmatter` builds the document title from project/audience/period/kind, and rollups passed `Project: ""`, which rendered as the literal "all subscribed projects". ACME's and GLOBEX's customer epic rollups therefore shipped an identical title and identical tags — nothing in the docbuilder index, where both are externally visible, said which customer a document belonged to. The `org::CODE` now travels in `Request.Project`, which the existing title and tag paths already read.
- **The rollup path now reports files that reached no branch.** `runAudienceRollups` discarded `Result.Closed` while the per-project path has always tracked it in `ProjectResult.FilesClosed`, so a re-run of a merged week printed `1 file(s) written (1 already published this week)` when nothing had reached `main`.
- **A file from a project that failed after writing it is now always reported.** `PartialFiles` printed only when some *other* project finished, and were not counted in the total — so the output listed two files under a `1 file(s) written` line, and a run where every project half-published said nothing at all about the files on the branch.
- **The two rollup renderers share one body-budget function.** `RenderRollup` and `RenderMonthlyRollup` each had their own copy of a drop loop that re-summed every surviving body on every iteration — O(n²), ~46 passes over a shrinking map on a 50-project run. One `capBodies`, measured once and subtracted, the shape `capEpicEntries` already used.
- **The per-group epic cache and the window bound are tested.** `groupEpics` and `runUntil` are the package's only mutable per-run state and have three separate seeding paths — `New`, the top of `Run`, and a lazy guard in `fetchProjectEpics` because `Pipeline`'s fields are exported and a struct literal is legal. None was covered. A Pipeline reused for a second week would have served week one's epics and filtered week two against week one's upper bound, silently.
- **The file-shape table in `docs/frontmatter-schema.md` was split in two** by a paragraph inserted mid-table, stranding the `monthly--<YYYY-MM>--<aud>.md` row into a headerless one-row table.
- **A monthly prompt test asserted the absence of a phrase** (`not strings.Contains(user, "Window:")`), which passes just as happily on a prompt with no header at all — the case it was written to catch. It now asserts the week manifest and the week count are present, which fails if the header is wrong rather than merely absent.

- **A project path's `/` becomes `@` in report filenames:** `group/sub/proj` writes `group@sub@proj--wk--team.md` instead of `group_sub_proj--wk--team.md`. The old mapping turned `/` into `_` and dropped `.`, so `group/a.b` and `group/ab` both produced `group_ab--wk--team.md`: the second run overwrote the first, and then read the first project's docbuilder UID back out of that file and published it on the second's report. One report lost, one cross-project link identity corrupted, silently, on a file marked `public: true`. `@` is legal in a filename and illegal in a GitLab project path, so it cannot collide with anything the path contains; both rejected alternatives still collide, and `TestSanitize_IsInjective` pins every case. **Migration:** a week already merged holds files under the old scheme; a re-run writes the new name and leaves the old one beside it. See docs/runbook.md.
- **The three per-project event listings stop paging at a ceiling.** `/merge_requests`, `/issues` and `/repository/commits` walked until GitLab returned an empty page, so a project with thousands of records in the window cost one round-trip per hundred records and held all of them. `maxEventPages` is 20 — 2,000 records per project per week. It is deliberately NOT `--max-events`: the cap has to agree with `prompt.capEvents`, which sorts on `merged_at` / `closed_at`, and no GitLab list endpoint can sort on those. Pinning the query to `updated_at DESC` and cutting at the cap returns the WRONG records — a label sweep over archived MRs bumps their `updated_at` to today, so the first page is the archive and the week's merges never come back. That is what `keepNewestMRs` exists to survive.
- **A run is bounded at six hours.** Each HTTP call is bounded at 60s and retried three times, so a hung upstream makes one LLM call take ~4 minutes and a capped 50-project run has a seven-hour worst case with nothing to stop it. Six hours is far above a real run, so it only fires on a stuck upstream, and it corrupts nothing: the period is computed once at start-up, so an aborted run still files under the week it began in and every file it already wrote is listed by the summary.
- **Releases build and test before they publish.** The release workflow went straight from checkout to goreleaser, so a tag pushed from a branch whose CI never went green shipped binaries and images. The local lefthook pre-commit is not a CI gate — it does not exist on a machine that never ran `lefthook install`. `go vet`, a build and the test suite now run first.

The branch is now resolved once, above the filename loop.
- **Three copies of the retry-and-status loop in one file.** `pageEpics`, `FetchProjectSummary` and `hasRepoRootFile` each built their own `for { attempt++ … switch resp.StatusCode … }` and had already drifted: one soft-degraded 403 and 404, another only 404. The cost was concrete — the last two audits each fixed the same thing by hand across every copy. All three use `doJSON`/`getPage` now, which is what the `soft` parameter was added for.
- **A documented Docker workflow failed on first use.** Neither Dockerfile declared `USER`, so the uid was inherited from the distroless base rather than stated, and the release notes told operators to mount a host directory for `--output-dir`. The process runs as 65532 and a host directory belongs to the host user, so the write fails with `permission denied`. `USER 65532:65532` is declared in both images and the uid is documented at the point of use.
- **`summarizer monthly` could read the wrong file, or none.** It looked for the weekly rollup by trying window sizes in turn and taking the first hit, so a week whose rollup was missing silently fed a different window's file into the month summary. With one window it names the file outright. That also settles the epic rollups: `combined--epics-rollup--wk--customer.md` and `combined--epics-acme--wk--customer.md` share the combined rollup's prefix and its audience suffix, so any pattern matching on those two attributes picks them up — which would have folded already-per-customer documents into one blob.

- **`summarizer` summarised the project it was writing to.** With `publish.enabled: true` the reports repo is an ordinary active project on the same host, so discovery found it, and its merge requests are summarizer's own publishing MRs. Every week spent an LLM call describing the previous week's reports — and because the activity gate never filters it (it is active every week by construction), nothing else would have caught it. Discovery now skips `publish.project` by default and says so in the log: `excluded (publish target): sfb/reports`. An explicit `--project <reports repo>` still runs it, since an explicit listing is the operator overriding a default — the same authority that wrote the `publish.project` line. Cross-host publishers are not skipped: that repo is invisible to the source scan anyway, and matching on path alone would exclude an unrelated same-named project.
- Because a topic is invisible to anyone reading the repository, the discovery log now names which signal excluded a project: `excluded (topic no-summarize): group/legacy-billing` versus `excluded (opt-out file): group/archive`.

- **`summarizer monthly` silently bypassed the prompt-injection guard.** `MonthlyRunner` had no `Guard` field and called the LLM directly, while every other call site went through `checkPrompt`. `safety.enabled: true` therefore applied to weekly runs and not to monthly ones — and the monthly input is last month's *published* text, which is itself LLM output derived from GitLab issue and MR bodies. A monthly run now takes a guard, gets the same `--safety-*` flags, and routes through the same shared `checkPrompt` as per-project and rollup prompts. `monthlyCmd` also gained `--safety-enabled`, `--safety-url` and `--safety-token`, and guard construction is shared with `runCmd` via `newGuard`.
- **The epic fetch made one sequential HTTP call per epic, and the cap ran afterwards.** `fetchProjectEpics` fetched every epic's issues and only then truncated to `maxActiveEpics = 20` in the caller, so a group with 120 epics cost 120 round-trips to produce a report using 20 of them — the dominant cost of a run once discovery stopped being opt-in, and it grew every quarter. The cap now runs before the per-epic fetch, so it bounds the HTTP calls as well as the output.
- **`--dry-run` paid the full epic fetch before bailing out.** The dry-run exit sat 35 lines below `fetchProjectEpics`, so the preview an operator runs *before* paying for a real run made hundreds of round-trips to produce output it discarded. It now returns as soon as the event counts are known.
- **The diff memory cap was applied after the allocation it claimed to prevent.** `FetchMRDetail` decoded `Diff` into a plain string and truncated to 600 runes afterwards, so the full body was materialised first — twice over with `io.ReadAll` — then thrown away, on every run including the default `--include-diffs=off` one that never reads the text. A `cappedDiff` type now truncates during decoding; `encoding/json` hands a custom unmarshaller a subslice of its input, so the oversized body is never allocated.
- **A partial run reported as a total failure.** `printSummary` printed nothing but an error message when a project failed, even though the loop had continued and published the rest — so 24-of-25 successes looked identical to 0-of-25. It now prints the successes and labels the run `PARTIAL`.
- **The LLM response body was read unbounded.** `io.ReadAll(resp.Body)` with no limit, in both providers, on the one path that talks to a host we do not control — and the error path truncates to 300 bytes anyway. Now bounded at 8 MB, far above any real completion.
- **Epic order was whatever GitLab returned.** `/epics` promises no ordering, and the slice is rendered into the prompt in that order, so two runs over identical input produced different documents and the fingerprint flagged churn that was not a content change. Epics are now sorted by IID first.
- **`--max-projects` kept a fixed cohort chosen by API response order.** `finalList[:cap]` on a list ending in discovered projects in API order meant ten projects were summarised every week and 190 never, permanently. The scan now ranks by `last_activity_at` and the budget applies to discoveries only; it still does not rotate — that is a policy decision, not a default.
- **The local-disk publisher discarded the period, so every week overwrote the last — silent data loss.** `Local.Publish` did `filepath.Join(l.Dir, req.Name)` and never read `req.Period`; only the GitLab publisher used it. Report filenames carry the window (`--7d`) but not the date, so week N and week N+1 produced the same path and the second destroyed the first. `publish.enabled` defaults to `false`, so this was the out-of-the-box path. Both publishers now write `<dir>/<period>/<name>`, matching the layout the docs had been claiming for local mode all along.
- **A failure on one project aborted the whole run, contradicting the comment that promised the opposite.** `Run()`'s per-project loop carried the comment *"Failures on one project don't stop the others"* and then returned on the first error. A rate-limited completion on project 1 of 25 meant 24 projects never ran, while earlier projects were already published to the branch. The loop now logs `summarizer: WARN <project> failed, continuing`, finishes the remaining projects, and returns the first error so the exit code still signals failure. Cross-project rollups are skipped when any project failed — a rollup over a partial set would read as a complete week.
- **A failed project was appended to the result as a zero value before the error check**, so the run summary could count a project with an empty name. The append now happens after the failure is handled.
- **`monthlyCmd` duplicated `runCmd`'s publisher setup and had dropped its checks.** It validated the token env but not `publish.project`, so `publish.enabled: true` with no project produced a bare 404 from `/api/v4/projects//…` instead of the clear message `run` gives. Both commands now share one `newPublisher`.
- **The epic rollup's "activity in window: N events" was a substring search.** `countEpicEvents` counted occurrences of the epic's *title* inside the rendered report body, so two epics sharing a title each reported the sum of both, and a title appearing in prose inflated the count — in a customer-facing document. It now counts the real epic annotations `AttachEpics` already puts on every issue event.

### Changed
- **The two LLM providers share one request path.** `postJSON` now does the marshal, retry, bounded read, status error and decode for both; the adapters keep only their URL, headers, body and response shape. The duplicated halves had already drifted once — OpenAI omits an empty `Authorization` header so local servers accept it, Anthropic always sends `x-api-key`. A test pins that difference.
- **The epic rollup printed project names outside the `<data>` block.** The only GitLab-derived text in that prompt the model was told to trust; it is inside now, like every other template's.
- **The epic cap selects before the activity filter runs.** Bounding the fetch means choosing epics before we know which are active, so the selector decides. `maxActiveEpics` sits far above the usual active count and a stderr line names the project and group when the cap bites; see the Fixed entries above for how it selects.
- **Lean.** `parseMonth` hand-validated a `YYYY-MM` string that `time.Parse("2006-01", …)` validates exactly, with a clearer error. Two packages each wrapped `textutil.Truncate` in a one-line `truncate` helper while already importing `textutil`; the wrappers are gone.

- **The lefthook comment no longer implies CI is the safety net for the document hooks.** It never was: `ci.yml` runs vet, golangci-lint, `go test -race` and govulncheck, while `markdownlint`, `docbuilder-lint`, `typos`, `gitleaks`, `shellcheck`, `actionlint` and `hadolint` run on the author's machine only. `docbuilder-lint` is the one that matters most — it validates `docs/frontmatter-schema.md`, the contract for the frontmatter every published file carries — and it skips *silently* when the `docbuilder` binary is missing or broken, so a green hook line can mean "never ran".
- **`--force` no longer exists, and two structs no longer carry a field nobody read.** `Options.Force` was set from the flag and never read; `Request.Force` was hardcoded `true` at all three `Publish` call sites and read by neither publisher. The README described the same flag two different ways on one page — "accepted and does nothing" at line 345, "`--force` overwrites" at line 400, the latter inside the Security section. This is `forceOverwrite()`'s successor outliving its function. Flag, both fields, and the contradictory line are gone.
- **`FetchEpicIssues` was a 56-line hand-rolled copy of `getAll`** — its own URL construction, retry loop, status dispatch, `X-Next-Page` handling and unmarshal, with zero calls to the shared helpers, and it had already drifted into being one of the six unbounded reads. `doJSON`, `getPage` and `getAll` now take the soft-degrade statuses that function needed; `FetchEpicIssues` is five lines. `pagedProjects`, a near-copy of `getAll` added last release, is gone too — `getAll` takes the page ceiling directly and reports whether it stopped early.
- **`pagedProjects`**, for the same reason.
- **Dead code left by the last two releases.** `publisher.ErrExists`, `Result.Skipped`, and `classify`'s branch for them were unreachable once weekly buckets made `forceOverwrite()` constant. `ProjectPolicy.Run` was set to `true` and read nowhere. `policy.Classify`'s `source` parameter was never read — the whole `ProjectSource` enum existed only to feed it, threaded through `Run()` → `runOneProject` for no effect. `lastSlash` and `atoi` reimplemented `strings.LastIndex` and `strconv.Atoi`. `ErrReadUnsupported` was exported and never called. Also: refuse-first is gone from the local publisher, which is what those three were supporting.

### Added
- **`--max-projects` (default 50) bounds the per-run bill.** Each project costs two completions, so the activity-default discovery could produce an unbounded number of calls on an instance where everything had been touched. Applied after discovery and opt-out so it never counts projects that would not have run, and before the first completion so dropping projects actually saves money. Dropped projects are listed on stderr. `0` means "use the default", not "no limit"; an explicit value below the default is honoured. (The discovery-side half — bounding the probes — landed with the fix below.)

Corrected, and the runbook's "Refuse overwrite (exit 6)" scenario now describes the real recovery path (git history on the period branch).
- **Seven registered flags were undocumented** — `--max-events`, `--gitlab-host`, `--gitlab-token`, `--openai-key`, `--anthropic-key`, `--safety-url`, `--safety-token`. A full flag reference now lives in the runbook, including the removed `--period-mode` and the no-op `--force`.

Q1 claimed `classify` was a pure string-match when it uses `errors.Is` for its two typed sentinels. `how-it-works.md` also listed "automatic enrollment of new projects" as out of scope; it shipped.

### Changed
- **Period directories are ISO week numbers.** `summarizer/2026-10-19/` → `summarizer/2026-W43/`, via Go's `ISOWeek()` so the ISO year-boundary rules apply (2027-01-01 is `2026-W53`, not `2027-W01`). Weekly buckets were already what `--period-mode monday` selected; this makes them the only option and removes the flag. A day-granular bucket can't be expressed as a week number — seven runs would collide on one directory — so `daily` went with it rather than being left as a mode that lies about its output. `--force` is now implied: every run in a week targets the same path, so refuse-first would fail the cron from day 2.
- **`--period-mode` removed.** Passing it is now a usage error.

### Added
- **`summarizer monthly` — month-end rollup over the weekly rollups.** Reads the previous calendar month's already-published weekly cross-project rollups back out of the target repo and writes one month-end file per audience (`reports/2026-09/monthly--2026-09--customer.md` and `--team.md`), on its own branch and MR so it never collides with a week's. Reading the published output rather than re-running the pipeline keeps this to one LLM call per audience instead of a second full pass of per-project calls, and means it rolls up exactly what was published and runs from any machine holding the reports token. Weeks with no published rollup are skipped and listed; a month with none at all is an error rather than an empty summary. `--month YYYY-MM` re-runs a past month, `--dry-run` prints the assembled prompt. Requires `publish.enabled` — a local-disk publisher has nothing to roll up.
- **Read capability on the GitLab publisher** (`ListPeriodBranches`, `ReadReportFile`). Filtered to the publisher's own `<prefix>/YYYY-Www` branches so the target's default branch, other tools' branches, and a person's feature work are all left out. A 404 on a file reports absence rather than erroring, so one unpublished week doesn't kill the month.
- **A week belongs to the month containing its Monday.** September 2026 collects W37–W40; the week of Aug 31 is a September-adjacent week that would otherwise be counted in both months. Covered by a 2026-12 case, since 2026 is a 53-week ISO year.

### Not changed
- Per-customer epic rollups (`combined--epics-<customer-slug>--*`) are deliberately excluded from the monthly summary. They are already split per customer; folding them into one blob would mix customers together, which is the opposite of what that split exists to prevent.

## [0.1.0] - 2026-10-21

First tagged release. Everything below shipped together under this one

### Changed
- **Discovery is opt-out, not opt-in.** Running with no discovery flag now runs every project the token can see that had activity in the window (`--discover-active`, using GitLab's server-side `last_activity_after` filter). Previously an operator with ~25 projects had to add a topic to each one before anything was summarised. Three changes ship together:
  - **Default audience is team-only for every project**, explicit or discovered. An operator naming a project with `--project` no longer unlocks customer-facing output by itself; only the `summarize` topic does. `summarize-team-only` and the `internal_only_projects` block keep working as team-only overrides.
  - **`.summaryignore` or `.docignore` in the repo root opts a project out of the run entirely.** Checked on the project's default branch before the activity probe, so an opted-out project costs two API calls and nothing else. The file wins over an explicit `--project` listing: the project owner's signal is more authoritative than the cron config. A 404 or 403 (confidential project) is not an error and does not opt out — the project runs on its defaults.
  - **`--discover-by-topic` is kept** as an escape hatch for instances where the activity net is too wide.

  Migration: projects that already carry `summarize` are unaffected. Projects with no topic that were previously only listed explicitly drop from customer-facing to team-only output. Projects nobody named and that had no topic start producing team-only reports — add `.summaryignore` to any of those you don't want.

### Fixed
- **Push-only repos were excluded from the run entirely.** `ProbeProjectActivity` probed merge requests, then issues, and stopped. `FetchCommits` was fetching default-branch commits and rendering them into the report, but a repo maintained by direct pushes to `main` — no MR, no issue — never got that far: the gate said quiet and the project was dropped. `last_activity_after` on the discovery scan sees those repos fine, so they were being proposed and then discarded, which made the activity-default discovery look broken for exactly the projects it was meant to surface. The gate now falls through to a third `repository/commits` probe. It runs last, so it costs a round-trip only for projects already quiet on MRs and issues.
- **Discovered projects were publishing customer-facing reports.** `runOneProject` classified with a hardcoded `policy.SourceExplicit`; `Run()` carried a comment claiming it overrode the field to `SourceDiscovered`, but only set `FromDiscovery`, and nothing else ever wrote `Source`. Every project surfaced by `--discover-group` or `--discover-by-topic` therefore classified as operator-named: a project with **no topics** returned `CustomerOn=true`, made a customer LLM call, and published a file with `public: true` — while the discovery manifest printed `(team-only)` from a separate, correct classification. D5's safe default was inverted; nobody had to set `summarize-team-only` to leak a project. The project origin now flows into the classifier, and `ProjectResult.Source` is gone so the two can no longer disagree.
- **`gitlab_host:` in the YAML config was silently ignored.** The field had no `yaml:` tag, so yaml.v3 looked for `gitlabhost`. `examples/summarizer.yaml` and the README both used `gitlab_host:`, and the resulting error said "set gitlab_host in config" — pointing at the key that did nothing. The entire config-file path was unusable without `--gitlab-host`.
- **A flaky LLM call aborted the whole run mid-way.** The GitLab client has retried 429/5xx three times with backoff since v0.1.0; the LLM providers retried nothing, and `Run()` returns on the first project error. One rate-limited completion killed a run that had already published files for earlier projects, leaving a half-week on the target branch with no rollup and nothing to distinguish it from a complete week. Both providers now retry on the same policy (Retry-After honoured and capped at 60s, exponential backoff capped at 30s, no jitter — the calls are sequential within one process), do not retry non-429 4xx, and stop immediately on context cancellation so Ctrl-C works.
- **`capEvents` claimed to keep the most recent events but did no sorting.** It returned `min(len, cap)`, and the pipeline concatenates MRs, then issues, then commits — so a busy commit week silently dropped the tail of the commits bucket regardless of date. It now sorts a copy (most-recent-first, kind+ref tiebreak) and returns the kept slice, leaving the caller's shared slice untouched.
- **`truncate` sliced bytes and could emit invalid UTF-8 into prompts.** Four byte-identical copies did `s[:n]`, splitting multi-byte characters: verified that `"Fix for kundeøkning…"` at cap 14 produced `"Fix for kunde\xc3..."` and an emoji at cap 8 produced `"Deploy \xf0..."`. It runs on every MR title and description in every prompt. One rune-aware `textutil.Truncate` now backs all four call sites.
- **The run summary miscounted files.** It reported `2 * len(projects) + rollups`, over-counting every team-only project (one file, not two) and ignoring the epic rollups, so an operator could not reconcile the target repo against the stderr line. It now counts what was actually published and lists the epic rollups.

### Removed
- **`projects:` in the config file.** `Config.Projects` parsed but was never read — an operator listing projects in YAML got "at least one --project… is required" with no hint their list was discarded. The field and its example are gone; the project set comes from `--project` / `--discover-group` / `--discover-by-topic`.

- **Fixed: `--discover-group` alone exited with `at least one --project is required`.** The CLI gate checked only `--project`, contradicting both the README and the pipeline's own gate. The gate now accepts `--project`, `--discover-group` or `--discover-by-topic`.
- **`--period-mode daily|monday`.** Controls the output bucket shape. `daily` (default, v0.1.0 behaviour) gives each cron tick its own `<prefix>/<YYYY-MM-DD>/` directory, branch and MR. `monday` anchors the bucket to the ISO week's Monday, so daily runs across Mon–Sun overwrite the same directory; the GitLab publisher accumulates commits on one branch and reuses the open MR, and the local-disk publisher implies `Force` so the cron doesn't start failing on day 2. Crossing into a new week opens a new bucket. Unknown values fail at parse time (case-sensitive; `weekly` is not accepted — the bucket is a date, not an ISO week number).
- **D5 — GitLab-as-control-plane audience policy** (D5 from `docs/deferred.md`). Three sources of "is this project customer-eligible" union together: the YAML `internal_only_projects:` block, the `--internal-only-project` CLI flag, and the GitLab project's topics (`summarize` for opt-in to customer output; `summarize-team-only` for the override). Discovered projects (via `--discover-group`) default to team-only unless `summarize` is set — the default-safe behavior keeps the customer side bounded even when the operator doesn't know what's in a group.
- **Cross-project epic rollup file** (`combined--epics--<period>--<audience>.md`). Fires whenever ≥1 active epic exists anywhere in the run, independent of project count. Each project's active epics land in dedicated `# Project: …` sections with title, state, web URL, and event count; the LLM synthesizes cross-project themes for both customer and team audiences. One extra LLM call per audience per run.
- **Epic-level rollup in per-project reports.** When a project's GitLab group has epics (Premium/Ultimate feature), the customer and team prompts surface them as `## Epics active this period` with one H3 per epic, linked issues nested underneath, and an `## Other activity` section for events without an epic link.
  - Activity gate: an epic only counts toward the `maxActiveEpics=20` cap when at least one of its linked issues has `updated_at` within the window. Dormant epics (no issue activity this period) are silently dropped — they don't surface in the report and don't burn the cap.
  - Auto-detected project → group mapping via `GET /projects/:id`. Summarizer reads `namespace.kind` and `namespace.full_path` from the project metadata; user-namespace projects (kind=`user`) bypass the `/epics` fetch with no extra config.
  - Graceful degradation: Free-tier GitLab (no `/epics`), wrong group path (404), or auth issues are all detected. 403/404 → empty epic section with a one-line stderr note; 401 → operator-visible error.
- **`--discover-group` flag for activity-based discovery.** Scan a GitLab group's projects, probe each one for activity (a single cheap MR-list call per project with `per_page=1`), and roll the active ones into the run alongside any explicit `--project` listings. Recursion into subgroups is reserved for a future change; v1 ships single-level only. Composable with `--project`; dedupes by project path (explicit listings take precedence on duplicates).
- **Discovery manifest to stderr.** Per-group scan summary with one line per scanned project (included / excluded with reason), plus a one-line totals. Diagnostic — not a separate file.

- `internal/prompt.Render(...)` signature gained a final `[]*gitlab.Epic` parameter. Pass `nil` for projects without epics to keep the existing flat rendering. All call sites and the existing test fixtures updated.
- `internal/run.ProjectResult` gained `Source`, `TeamOnly`, `CustomerOn` fields carrying the D5 audience policy forward so rollup filters don't recompute.

### Internals (epics)
- New `Epic` and `Namespace` types in `internal/gitlab`. `Epic.StartDate` and `Epic.DueDate` use a custom `Date` decoder that accepts both `YYYY-MM-DD` (GitLab's epic schema) and RFC3339.
- `FetchEpics` and `FetchEpicIssues` are paginated like the existing fetchers but carry a soft-degrade contract for 403/404 (Free-tier / wrong group), distinct from the existing `getPage` path. 401s and 5xxs hard-fail (auth/transport).
- New `events.AttachEpics` correlates issue events with their containing epic by IID. Commits and MRs are intentionally NOT annotated (no issue-linkage in this code path).
- New `events.FilterActiveEpics(window)` is the half-open `[since, until]` filter that the pipeline runs before the cap.

### Internals (discovery)
- New `gitlab.ProjectSummary`, `gitlab.FetchGroupProjects(ctx, group, recursive)`, `gitlab.ProbeProjectActivity(ctx, project, since)`. Probe uses `per_page=1` and a soft-degrade contract (404 → inactive; 403 → hard error). `ProjectSummary.Topics` carries the project's GitLab topic list (used by D5 audience policy).
- New `gitlab.FetchProjectSummary(ctx, projectPath)` — single-project `/projects/:id` fetch used by the audience-policy classifier. Soft-degrades 404 → (nil, nil).
- New `run.Options.DiscoveredGroups` field. `ProjectResult.FromDiscovery` (new bool) flags per-project whether the project came from discovery vs. explicit listing.

### Internals (D5 / audience policy)
- New `internal/policy` package — `ProjectSource` enum (`SourceExplicit`, `SourceDiscovered`), `ProjectPolicy`, and a pure-function `Classify(source, topics, inList)`. The 13-row truth table is the project's truth-table test (`policy_test.go`). Topics are case-sensitive exact-token matches (`"summarize-team-only"` is a distinct label from `"Summarize-Team-Only"`).
- Discovery manifest annotates each scanned project with a `(team-only)` tag when the classifier says so, so the operator's stderr audit trail tells them what's classified how.
