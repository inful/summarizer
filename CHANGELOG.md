# Changelog

All notable changes to summarizer are documented here. The format is
based on [Keep a Changelog](https://keepachangelog.com/), and this
project adheres to [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Changed
- **The default window is now the ISO week, not a rolling 7 days.** Reports are filed under `summarizer/2026-W43/`, and the window was `now - 168h`, so the two disagreed. Run on a Monday and the file named `2026-W43` held nothing at all from week 43 and a full week of week 42 — which reads, correctly, as a bug. On a Thursday the same command looked three weeks into the past. The default is now Monday 00:00 UTC to now (`run.WeekWindow`), matching the directory the output lands in. `--since` and `default_lookback` still override it for a deliberate backfill; the config default of `default_lookback: "168h"` is gone, so an unset value now means "this week".
- **Filenames say `wk` rather than a day count.** With a week-to-date window, `--<N>d--` rendered as however many whole days had elapsed — `3d` on a Thursday — so the same week's file was renamed daily and no two days agreed on what it covered. The week default is `wk` throughout the week; an explicit `--since` keeps its `--7d--` / `--30d--` spelling.

### Fixed
- **`summarizer monthly` skipped every week that had epics.** The ambiguity check I added for a stale window matched candidates on prefix and suffix, and `combined--epics-rollup--wk--customer.md` and `combined--epics-acme--wk--customer.md` carry the same prefix and the same suffix as `combined--rollup--wk--customer.md`. Any project with epics produced two or more "candidates", the week was reported as ambiguous and dropped — and the error named the epic files as if they were competing windows. The check now matches on the kind segment, which is the only thing that distinguishes them. Segment count does not work either: `epics-rollup` holds a single `-`, so it splits into the same four `--` segments as the file wanted. The epic-rollup exclusion that function's comment promised was, since that commit, not actually happening.
- **`max_events` bounded the prompt, not the requests that build it.** `runOneProject` called `fillMRDetail` — one `GET /merge_requests/:iid/changes` per MR — before `capEvents` ran inside `prompt.Render`. A project with 300 MRs in a 30-day window cost 300 sequential requests, and the one flag an operator reaches for to bound cost did nothing about any of them, because the data was already gone by the time anything was trimmed. The MR list is now trimmed to `max_events` *before* the fetch, using the same newest-first/IID-tiebreak ordering as `capEvents` so the two agree on what "the newest n" means. Same for the assembly of the event slice: it moved after the fill, so no event in the prompt can be missing the `/changes` data behind it.
- **`--dry-run` paid the per-MR fetch it then threw away.** The dry-run exit sat *below* `fillMRDetail`, so a preview made one request per merge request per project before discarding everything. An earlier audit moved the *epic* fetch and left this one. The exit now sits after the three list calls — whose counts are exactly what the preview reports — and before every per-item request.
- **Every GitLab response body was read into memory without a bound.** Six `io.ReadAll(resp.Body)` calls, one of them serving `/merge_requests/:iid/changes`. `cappedDiff` truncates the `Diff` field at decode time, so the string is never allocated twice — but the raw response was already fully resident to get there, and `fillMRDetail` runs four of those concurrently. The LLM package had already fixed exactly this and left a comment saying why; the GitLab side never did. All six now go through `io.LimitReader` at 16 MB.
- **Every rollup was published with a garbled title and a sentence for a tag.** `Request.Title` was passed as `NewFrontmatter`'s `audience` parameter. That worked on exactly one of five paths — per-project sets `Title` to `"customer"`, so the slot was right by coincidence — while combined rollups set `"rollup customer"`, epics `"epics rollup customer"`, per-customer `"epics rollup for ACME customer"`, and monthly `"monthly rollup customer"`. Those landed in the title format string as *"Cross-project rollup rollup customer report — all subscribed projects, 2026-W42"*, and in `Tags`, where the audience tag was a whole phrase rather than a searchable token. `Request` now has an `Audience` field, set from `string(aud)` at every call site where it was already in scope.
- **The OpenAI key check missed two of the three base-URL spellings the normaliser accepts.** The guard was a literal compare against `"https://api.openai.com/v1"`, but `normalizeBaseURL` treats that, `https://api.openai.com`, and a trailing-slash form as the same host — and the config comment says the bare form is supported. Set `openai_base_url: https://api.openai.com` without `OPENAI_API_KEY` and the run sent unauthenticated requests to api.openai.com for every completion, retried four times each, with no message at start-up. The check is now `llm.IsOpenAIHost`.
- **`FilterActiveEpics` documented the opposite of the order it runs in.** The comment said the cap applies to the filtered slice so "inactive epics never appear regardless of how many exist". Since the cap moved ahead of the filter, that is no longer the mechanism — an inactive epic that was not selected was never fetched. The comment described the guarantee a reader would most want to be true.
- **`injection_threshold: 1.0` was silently rewritten to 0.7.** The clamp shared its branch with the unset-value check (`<= 0 || >= 1`). 1.0 is a legitimate "block everything" reading.

- **`--max-projects` capped *candidates examined*, not *projects run*.** The budget was moved into the activity scan so discarded projects would stop costing HTTP calls — which changed what it capped. `for n, proj := range projects { if n >= limit { break } }` counts candidates, so an instance whose most-recently-active projects were all opted out, or had a push but no MR/issue/commit in the window, examined `maxProjects` of them, included none, and published **zero** reports while logging the rest as "not considered". The budget now counts inclusions: the scan keeps admitting until the run holds `maxProjects` projects. Same HTTP saving, the original meaning. This is the second time a cap moved earlier and silently changed its subject (the first was the epic cap below); both had tests asserting the *optimisation* rather than the outcome.
- **`--max-projects` could drop a project the operator named.** `Run()` sorted explicit `--project` entries and discovered ones into one alphabetical pool and cut it at the cap, so `--project z-team/critical` was evicted by any discovered `a-*` project. An explicit listing is a statement of intent; the cap is a cost guard for a wide sweep. They no longer compete: the cap applies only to what discovery contributes, and an explicit list larger than the cap runs in full with a warning instead of being truncated.
- **The monthly rollup read whichever window size it found first.** A weekly branch keeps every file it ever received and the window is part of the filename (`combined--1d--…` vs `combined--7d--…`), so changing `--since` mid-week leaves both behind. The reader tried 1d, 7d, 14d, 30d in order and took the first hit — feeding a **one-day** rollup into the month summary as the week's input, without a word. The Files API returns no modification time, so there is no honest way to pick; the runner now lists the week's directory, and a week carrying more than one window is named and skipped rather than guessed at. One bad week no longer costs the other three.
- **The epic cap reverted to oldest-first when the API omits `updated_at`.** If every timestamp is the zero time the recency sort ties throughout and the IID tiebreak hands back the 20 *lowest* IIDs — exactly the bug the sort exists to prevent — while the log still claimed "most recently updated". A GitLab that omits the field (older version, permissions-filtered response) makes the fix conditional on data the code does not control. When no epic carries a timestamp the runner now says so and keeps the highest IIDs, which are newer by construction.
- **`--discover-group` had no cap at all, unlike `--discover-active`.** The same scan, ~1,500 sequential round-trips on a 500-project group, no ceiling and no message — and the newer flag is the one an operator is most likely to reach for now that discovery is on by default. All three discovery loops share one budget now.
- **Every merge request described itself with the file *kind* under a heading that said "Audience".** `- **Audience:** per-project` names a category, not an audience; the real answer (`customer-facing` vs `internal`) was nowhere in the body. Replaced by a `- **Visibility:**` row, adjacent to the earlier `Project(s)` fix in the same template.
- **The activity scan paged `/projects` without a ceiling.** On an instance where the token can see thousands of projects it walked every page and held every `ProjectSummary` in memory, to then rank them and keep at most `maxProjects` — and the first page is already the most recently active hundred, because the query asks for `order_by=last_activity_at`. Bounded at 10 pages with a log line when the scan stops early, so a truncated scan is never presented as complete.
- **`Config`'s doc comment listed the pre-inversion discovery flags** and described `internal_only_projects` without saying it is an audience switch rather than an opt-out — the exact thing an operator reads when wondering why a list did nothing.

- **The epic cap silently emptied customer-facing rollups.** Capping the per-epic issue fetch before the activity filter — which is what bounded the HTTP calls — meant the cap chose which epics were even *considered*, and it chose by IID. So it kept the 20 *oldest* epics, filtered those by activity, and reported almost nothing: a group whose active epics all have high IIDs was never fetched and could not be reported. Selection is now by `updated_at` descending, which costs nothing because it arrives in the same `/epics` response; the surviving epics are re-sorted by IID for stable rendering. The HTTP bound is identical.
- **An explicit `--project` silently overrode a project's own opt-out.** When the discovery model was inverted the operator chose "the file wins over an operator's explicit listing", and the code said so in a comment — but explicit projects were appended to the run list unconditionally and never reached the opt-out check at all. A project carrying `.summaryignore` (or now `no-summarize`) would still be summarised if a cron line named it. Explicit projects now pass through the same `optOutReason` gate as discovered ones.
- **`--max-projects` bounded only the LLM bill, not the API bill.** Discovery still probed every active project — opt-out file read plus activity probe, roughly six sequential round-trips each — and `Run()` trimmed the resulting list afterwards. On an instance with 200 active projects that was ~1,200 requests spent building a list cut to 50. The activity scan now ranks candidates by `last_activity_at` (already in the payload) and stops admitting at the cap, so discarded projects cost nothing.
- **The GitLab publisher ignored the context.** Four request sites used `http.NewRequest` rather than `NewRequestWithContext`, so Ctrl-C could not interrupt a publish — only the reads and the LLM calls. `Publisher.Publish`, the branch/read helpers, and the monthly read path all take a context now, so the cancellation the runbook and the retry comment describe is true of the write path too.
- **The "nothing to run" line printed hardcoded zeros.** It said `explicit=0, discovered=0` as literals, which after the opt-out change contradicted the `excluded (topic no-summarize)` lines printed immediately above it. It now reports the real excluded count.
- **Every rollup MR described itself with filenames.** The MR body printed `req.Name` under a `- **Project(s):**` heading, which is right for a per-project file and wrong for every rollup — the reviewer-facing MR said `Project(s): combined--epics-acme--7d--customer.md`. The row is now omitted when there is no single project.
- **`res.AnnotatedEvents` retained every event of every epic-bearing project** for the whole run, when the only consumers wanted twenty integers per project. The counts are now computed in `runOneProject` while the events are in scope and stored as `map[int]int`.
- **Two hand-rolled helpers duplicated the stdlib.** `containsString` justified itself with "slices.Contains would add an import" — on a file that now imports `slices`. Both it and `policy.hasTopic` are replaced by `slices.Contains`.
- **`forceOverwrite()` was a function that always returned `true`**, kept alive only by a comment promising a home for a future `--period-mode` that no longer exists. Removed; the two call sites pass `Force: true` and say why.
- **Regression tests for all six fixes above.** Both cap bugs had passing tests, because the tests asserted that requests were bounded rather than that projects were included — which is why neither showed up until the diff was read rather than the intent.
- **Six comments described behaviour that had been deleted**, including a `// nolint:unused` on `fetchProjectEpics`, which told the linter to ignore a function that is very much wired, and two `filename()` comments citing a refuse-first policy that stopped existing three releases ago.


### Added
- **`no-summarize` GitLab topic — an opt-out that costs one click and no commit.** The `summarize` topic opted a project *in* to customer output, but opting *out* of the run was only possible via a `.summaryignore` / `.docignore` file, which needs a commit and a merge and puts noise in a project's history for something that is not a code change. A topic is a one-click reversible toggle, which is what you want for "noisy this sprint, skip it for a fortnight" or a repo you administer in GitLab but should not be pushing branches into. It is checked first because it is free — the topics already arrive with the project summary — and it short-circuits the file read entirely. It wins over `summarize` and over an explicit `--project`. Naming follows GitLab's own exclusion convention (`no-issue`, `no label`, `skip ci`). Icon: `docs/topics/no-summarize.svg` plus a 192×192 PNG render, matching the existing two.
- **`summarizer` summarised the project it was writing to.** With `publish.enabled: true` the reports repo is an ordinary active project on the same host, so discovery found it, and its merge requests are summarizer's own publishing MRs. Every week spent an LLM call describing the previous week's reports — and because the activity gate never filters it (it is active every week by construction), nothing else would have caught it. Discovery now skips `publish.project` by default and says so in the log: `excluded (publish target): sfb/reports`. An explicit `--project <reports repo>` still runs it, since an explicit listing is the operator overriding a default — the same authority that wrote the `publish.project` line. Cross-host publishers are not skipped: that repo is invisible to the source scan anyway, and matching on path alone would exclude an unrelated same-named project.
- Because a topic is invisible to anyone reading the repository, the discovery log now names which signal excluded a project: `excluded (topic no-summarize): group/legacy-billing` versus `excluded (opt-out file): group/archive`.

- **`summarizer monthly` silently bypassed the prompt-injection guard.** `MonthlyRunner` had no `Guard` field and called the LLM directly, while every other call site went through `checkPrompt`. `safety.enabled: true` therefore applied to weekly runs and not to monthly ones — and the monthly input is last month's *published* text, which is itself LLM output derived from GitLab issue and MR bodies. A monthly run now takes a guard, gets the same `--safety-*` flags, and routes through the same shared `checkPrompt` as per-project and rollup prompts. `monthlyCmd` also gained `--safety-enabled`, `--safety-url` and `--safety-token`, and guard construction is shared with `runCmd` via `newGuard`.
- **The epic fetch made one sequential HTTP call per epic, and the cap ran afterwards.** `fetchProjectEpics` fetched every epic's issues and only then truncated to `maxActiveEpics = 20` in the caller, so a group with 120 epics cost 120 round-trips to produce a report using 20 of them — the dominant cost of a run once discovery stopped being opt-in, and it grew every quarter. The cap now runs before the per-epic fetch, so it bounds the HTTP calls as well as the output.
- **`--dry-run` paid the full epic fetch before bailing out.** The dry-run exit sat 35 lines below `fetchProjectEpics`, so the preview an operator runs *before* paying for a real run made hundreds of round-trips to produce output it discarded. It now returns as soon as the event counts are known.
- **The diff memory cap was applied after the allocation it claimed to prevent.** `FetchMRDetail` decoded `Diff` into a plain string and truncated to 600 runes afterwards, so the full body was materialised first — twice over with `io.ReadAll` — then thrown away, on every run including the default `--include-diffs=off` one that never reads the text. A `cappedDiff` type now truncates during decoding; `encoding/json` hands a custom unmarshaller a subslice of its input, so the oversized body is never allocated.
- **A partial run reported as a total failure.** `printSummary` printed nothing but an error message when a project failed, even though the loop had continued and published the rest — so 24-of-25 successes looked identical to 0-of-25. It now prints the successes and labels the run `PARTIAL`.
- **The LLM response body was read unbounded.** `io.ReadAll(resp.Body)` with no limit, in both providers, on the one path that talks to a host we do not control — and the error path truncates to 300 bytes anyway. Now bounded at 8 MB, far above any real completion.
- **Epic order was whatever GitLab returned.** `/epics` promises no ordering, and the slice is rendered into the prompt in that order, so two runs over identical input produced different documents and the fingerprint flagged churn that was not a content change. Epics are now sorted by IID first.
- **`--max-projects` kept a fixed cohort chosen by API response order.** `finalList[:cap]` on a list ending in discovered projects in API order meant ten projects were summarised every week and 190 never, permanently. The scan now ranks by `last_activity_at` and the budget applies to discoveries only; it still does not rotate — that is a policy decision, not a default.
- **The local-disk publisher discarded the period, so every week overwrote the last — silent data loss.** `Local.Publish` did `filepath.Join(l.Dir, req.Name)` and never read `req.Period`; only the GitLab publisher used it. Report filenames carry the window (`--7d`) but not the date, so week N and week N+1 produced the same path and the second destroyed the first. `publish.enabled` defaults to `false`, so this was the out-of-the-box path. Both publishers now write `<dir>/<period>/<name>`, matching the layout the docs had been claiming for local mode all along.
- **A failure on one project aborted the whole run, contradicting the comment that promised the opposite.** `Run()`'s per-project loop carried the comment *"Failures on one project don't stop the others"* and then returned on the first error. A rate-limited completion on project 1 of 25 meant 24 projects never ran, while earlier projects were already published to the branch. The loop now logs `summarizer: WARN <project> failed, continuing`, finishes the remaining projects, and returns the first error so the exit code still signals failure. Cross-project rollups are skipped when any project failed — a rollup over a partial set would read as a complete week.
- **A failed project was appended to the result as a zero value before the error check**, so the run summary could count a project with an empty name. The append now happens after the failure is handled.
- **`monthlyCmd` duplicated `runCmd`'s publisher setup and had dropped its checks.** It validated the token env but not `publish.project`, so `publish.enabled: true` with no project produced a bare 404 from `/api/v4/projects//…` instead of the clear message `run` gives. Both commands now share one `newPublisher`.
- **The epic rollup's "activity in window: N events" was a substring search.** `countEpicEvents` counted occurrences of the epic's *title* inside the rendered report body, so two epics sharing a title each reported the sum of both, and a title appearing in prose inflated the count — in a customer-facing document. It now counts the real epic annotations `AttachEpics` already puts on every issue event.

### Changed
- **The two LLM providers share one request path.** `postJSON` now does the marshal, retry, bounded read, status error and decode for both; the adapters keep only their URL, headers, body and response shape. The duplicated halves had already drifted once — OpenAI omits an empty `Authorization` header so local servers accept it, Anthropic always sends `x-api-key`. A test pins that difference.
- **The epic cap selects before the activity filter runs.** Bounding the fetch means choosing epics before we know which are active, so the selector decides. `maxActiveEpics` sits far above the usual active count and a stderr line names the project and group when the cap bites; see the Fixed entries above for how it selects.
- **Lean.** `parseMonth` hand-validated a `YYYY-MM` string that `time.Parse("2006-01", …)` validates exactly, with a clearer error. Two packages each wrapped `textutil.Truncate` in a one-line `truncate` helper while already importing `textutil`; the wrappers are gone.

### Removed
- **`--force` no longer exists, and two structs no longer carry a field nobody read.** `Options.Force` was set from the flag and never read; `Request.Force` was hardcoded `true` at all three `Publish` call sites and read by neither publisher. The README described the same flag two different ways on one page — "accepted and does nothing" at line 345, "`--force` overwrites" at line 400, the latter inside the Security section. This is `forceOverwrite()`'s successor outliving its function. Flag, both fields, and the contradictory line are gone.
- **`FetchEpicIssues` was a 56-line hand-rolled copy of `getAll`** — its own URL construction, retry loop, status dispatch, `X-Next-Page` handling and unmarshal, with zero calls to the shared helpers, and it had already drifted into being one of the six unbounded reads. `doJSON`, `getPage` and `getAll` now take the soft-degrade statuses that function needed; `FetchEpicIssues` is five lines. `pagedProjects`, a near-copy of `getAll` added last release, is gone too — `getAll` takes the page ceiling directly and reports whether it stopped early.
- **`pagedProjects`**, for the same reason.
- **Dead code left by the last two releases.** `publisher.ErrExists`, `Result.Skipped`, and `classify`'s branch for them were unreachable once weekly buckets made `forceOverwrite()` constant. `ProjectPolicy.Run` was set to `true` and read nowhere. `policy.Classify`'s `source` parameter was never read — the whole `ProjectSource` enum existed only to feed it, threaded through `Run()` → `runOneProject` for no effect. `lastSlash` and `atoi` reimplemented `strings.LastIndex` and `strconv.Atoi`. `ErrReadUnsupported` was exported and never called. Also: refuse-first is gone from the local publisher, which is what those three were supporting.

### Added
- **`--max-projects` (default 50) bounds the per-run bill.** Each project costs two completions, so the activity-default discovery could produce an unbounded number of calls on an instance where everything had been touched. Applied after discovery and opt-out so it never counts projects that would not have run, and before the first completion so dropping projects actually saves money. Dropped projects are listed on stderr. `0` means "use the default", not "no limit"; an explicit value below the default is honoured. (The discovery-side half — bounding the probes — landed with the fix below.)

## [0.2.0] - 2026-10-21

### Fixed
- **Docs cited code that no longer existed.** `how-it-works.md` named `FetchMRChanges`, `fillMRChanges` and `resolveOptions`; the source has `FetchMRDetail`, `fillMRDetail` and `resolveProjects`. The same diagram omitted discovery entirely, and every doc showed the rollup filenames as `combined--<days>d--<aud>.md` / `combined--epics--<days>d--<aud>.md` when `rollupFilename` has always emitted an explicit kind segment (`combined--rollup--`, `combined--epics-rollup--`, `combined--epics-<customer-slug>--`). The filenames were wrong in v0.1.0 too. The publisher's package comment and the runbook also described a plain PUT; the publisher dispatches POST-on-404 / PUT-on-200.
- **`docs/frontmatter-schema.md` documented a safety property the code no longer has.** It claimed the local publisher's refuse-first policy preserves UIDs across re-runs. `forceOverwrite()` has returned `true` since the week buckets landed, so refuse-first is unreachable and `--force` is a no-op. Corrected, and the runbook's "Refuse overwrite (exit 6)" scenario now describes the real recovery path (git history on the period branch).
- **Seven registered flags were undocumented** — `--max-events`, `--gitlab-host`, `--gitlab-token`, `--openai-key`, `--anthropic-key`, `--safety-url`, `--safety-token`. A full flag reference now lives in the runbook, including the removed `--period-mode` and the no-op `--force`.
- **`docs/deferred.md` was two entries out of date.** Q2 claimed `internal/run` had zero test files (it has 11) and described activity discovery as flag-gated when it is now the default. Q1 claimed `classify` was a pure string-match when it uses `errors.Is` for its two typed sentinels. `how-it-works.md` also listed "automatic enrollment of new projects" as out of scope; it shipped.

### Changed
- **Period directories are ISO week numbers.** `summarizer/2026-10-19/` → `summarizer/2026-W43/`, via Go's `ISOWeek()` so the ISO year-boundary rules apply (2027-01-01 is `2026-W53`, not `2027-W01`). Weekly buckets were already what `--period-mode monday` selected; this makes them the only option and removes the flag. A day-granular bucket can't be expressed as a week number — seven runs would collide on one directory — so `daily` went with it rather than being left as a mode that lies about its output. `--force` is now implied: every run in a week targets the same path, so refuse-first would fail the cron from day 2.
- **`--period-mode` removed.** Passing it is now a usage error.

### Added
- **`summarizer monthly` — month-end rollup over the weekly rollups.** Reads the previous calendar month's already-published weekly cross-project rollups back out of the target repo and writes one month-end file per audience (`reports/2026-09/monthly--2026-09--customer.md` and `--team.md`), on its own branch and MR so it never collides with a week's. Reading the published output rather than re-running the pipeline keeps this to one LLM call per audience instead of a second full pass of per-project calls, and means it rolls up exactly what was published and runs from any machine holding the reports token. Weeks with no published rollup are skipped and listed; a month with none at all is an error rather than an empty summary. `--month YYYY-MM` re-runs a past month, `--dry-run` prints the assembled prompt. Requires `publish.enabled` — a local-disk publisher has nothing to roll up.
- **Read capability on the GitLab publisher** (`ListPeriodBranches`, `ReadReportFile`). Filtered to the publisher's own `<prefix>/YYYY-Www` branches so the target's default branch, other tools' branches, and a person's feature work are all left out. A 404 on a file reports absence rather than erroring, so one unpublished week doesn't kill the month.
- **A week belongs to the month containing its Monday.** September 2026 collects W37–W40; the week of Aug 31 is a September-adjacent week that would otherwise be counted in both months. Covered by a 2026-12 case, since 2026 is a 53-week ISO year.

### Not changed
- Per-customer epic rollups (`combined--epics-<customer-slug>--*`) are deliberately excluded from the monthly summary. They are already split per customer; folding them into one blob would mix customers together, which is the opposite of what that split exists to prevent.

## [0.1.0] - 2026-10-21

First tagged release. Everything below shipped together under this one
version — the earlier `[Unreleased]` and provisional `[0.1.0]`
sections were written before any tag existed and never described a
real published artifact.

### Changed
- **Discovery is opt-out, not opt-in.** Running with no discovery flag now runs every project the token can see that had activity in the window (`--discover-active`, using GitLab's server-side `last_activity_after` filter). Previously an operator with ~25 projects had to add a topic to each one before anything was summarised. Three changes ship together:
  - **Default audience is team-only for every project**, explicit or discovered. An operator naming a project with `--project` no longer unlocks customer-facing output by itself; only the `summarize` topic does. `summarize-team-only` and the `internal_only_projects` block keep working as team-only overrides.
  - **`.summaryignore` or `.docignore` in the repo root opts a project out of the run entirely.** Checked on the project's default branch before the activity probe, so an opted-out project costs two API calls and nothing else. The file wins over an explicit `--project` listing: the project owner's signal is more authoritative than the cron config. A 404 or 403 (confidential project) is not an error and does not opt out — the project runs on its defaults.
  - **`--discover-by-topic` is kept** as an escape hatch for instances where the activity net is too wide.

  Migration: projects that already carry `summarize` are unaffected. Projects with no topic that were previously only listed explicitly drop from customer-facing to team-only output. Projects nobody named and that had no topic start producing team-only reports — add `.summaryignore` to any of those you don't want.

### Fixed
- **Push-only repos were excluded from the run entirely.** `ProbeProjectActivity` probed merge requests, then issues, and stopped. `FetchCommits` was fetching default-branch commits and rendering them into the report, but a repo maintained by direct pushes to `main` — no MR, no issue — never got that far: the gate said quiet and the project was dropped. `last_activity_after` on the discovery scan sees those repos fine, so they were being proposed and then discarded, which made the activity-default discovery look broken for exactly the projects it was meant to surface. The gate now falls through to a third `repository/commits` probe. It runs last, so it costs a round-trip only for projects already quiet on MRs and issues.
- **Discovered projects were publishing customer-facing reports.** `runOneProject` classified with a hardcoded `policy.SourceExplicit`; `Run()` carried a comment claiming it overrode the field to `SourceDiscovered`, but only set `FromDiscovery`, and nothing else ever wrote `Source`. Every project surfaced by `--discover-group` or `--discover-by-topic` therefore classified as operator-named: a project with **no topics** returned `CustomerOn=true`, made a customer LLM call, and published a file with `public: true` — while the discovery manifest printed `(team-only)` from a separate, correct classification. D5's safe default was inverted; nobody had to set `summarize-team-only` to leak a project. The project origin now flows into the classifier, and `ProjectResult.Source` is gone so the two can no longer disagree.
- **`gitlab_host:` in the YAML config was silently ignored.** The field had no `yaml:` tag, so yaml.v3 looked for `gitlabhost`. `examples/summarizer.yaml` and the README both used `gitlab_host:`, and the resulting error said "set gitlab_host in config" — pointing at the key that did nothing. The entire config-file path was unusable without `--gitlab-host`.
- **A flaky LLM call aborted the whole run mid-way.** The GitLab client has retried 429/5xx three times with backoff since v0.1.0; the LLM providers retried nothing, and `Run()` returns on the first project error. One rate-limited completion killed a run that had already published files for earlier projects, leaving a half-week on the target branch with no rollup and nothing to distinguish it from a complete week. Both providers now retry on the same policy (Retry-After honoured and capped at 60s, exponential backoff capped at 30s, no jitter — the calls are sequential within one process), do not retry non-429 4xx, and stop immediately on context cancellation so Ctrl-C works.
- **`capEvents` claimed to keep the most recent events but did no sorting.** It returned `min(len, cap)`, and the pipeline concatenates MRs, then issues, then commits — so a busy commit week silently dropped the tail of the commits bucket regardless of date. It now sorts a copy (most-recent-first, kind+ref tiebreak) and returns the kept slice, leaving the caller's shared slice untouched.
- **`truncate` sliced bytes and could emit invalid UTF-8 into prompts.** Four byte-identical copies did `s[:n]`, splitting multi-byte characters: verified that `"Fix for kundeøkning…"` at cap 14 produced `"Fix for kunde\xc3..."` and an emoji at cap 8 produced `"Deploy \xf0..."`. It runs on every MR title and description in every prompt. One rune-aware `textutil.Truncate` now backs all four call sites.
- **The run summary miscounted files.** It reported `2 * len(projects) + rollups`, over-counting every team-only project (one file, not two) and ignoring the epic rollups, so an operator could not reconcile the target repo against the stderr line. It now counts what was actually published and lists the epic rollups.

### Removed
- **`projects:` in the config file.** `Config.Projects` parsed but was never read — an operator listing projects in YAML got "at least one --project… is required" with no hint their list was discarded. The field and its example are gone; the project set comes from `--project` / `--discover-group` / `--discover-by-topic`.

### Added
- **Ecosystem tooling.** Report UID is a UUID v7 minted by [`inful/mdid`](https://github.com/inful/mdid) (was: a hand-rolled 16-char SHA-256-hex truncation); the mint is non-deterministic by design, and cross-run stability comes from read-before-write in the GitLab publisher, which reads the existing file's frontmatter via [`inful/mdfm`](https://github.com/inful/mdfm) and reuses the existing UID on every re-run. Report fingerprint goes through [`inful/mdfp`](https://github.com/inful/mdfp)'s `CalculateFingerprintFromParts` (was: an inline `crypto/sha256` of the body bytes); output format is unchanged (SHA-256 hex). Two new direct dependencies (`mdid`, `mdfp`), one transitive (`mdfm`).
- **Topic icon assets.** `docs/topics/` ships SVG sources and 192×192 PNG renders for both `summarize*` topics, under GitLab's 200 KiB avatar limit, plus a README mapping each topic to its meaning.
- **`internal/textutil`** — one rune-aware `Truncate` replacing four byte-slicing copies.
- **Test coverage for the previously untested trust boundaries.** `internal/config` (key binding, defaults, validation — the missing `yaml_host` tag survived precisely because this was 0%), `internal/publisher` Local (refuse-first, force, temp-file cleanup on every path), `internal/llm` Anthropic (retries, `x-api-key`/`anthropic-version` header shape — the provider had never executed), and GitLab pagination (multi-page walks, the empty-page-with-next-header hang, `updated_after` surviving pagination). Total coverage 72.8%.
- **Exit codes 8 and 1 documented.** `classify` returns named constants and matches `run.ErrInjection` via `errors.Is` rather than by substring.
- `runRollup` and `runEpicRollup` now share one audience loop (`runAudienceRollups`), so the D5 customer/team boundary lives in one place instead of two verbatim copies.
- `FetchMRChanges` and `FetchMRDetail` collapsed into one `FetchMRDetail` returning both the aggregate and the chunks from a single `/changes` call. With `--include-diffs` the pipeline previously made two identical authenticated round-trips and two full JSON decodes per MR.
- `go.mod` bumped 1.26.9 → 1.26.10 for GO-2026-6809 (`crypto/x509`).
- **Fixed: every GitLab publish after the first file in a run failed with `400 Branch already been taken`.** `ensureBranch` POSTed `/repository/branches` unconditionally on each `Publish`, and GitLab 400s a duplicate branch name. Since every run publishes several reports into one period, only the first could ever land. `ensureBranch` now GETs the branch first and only POSTs on 404. The test fake had been returning 200 for a duplicate branch, masking the bug — it now returns 400 like GitLab does, and `TestGitLabPublisher_MultipleFilesOneBranch` covers the multi-file case.
- **`--discover-by-topic` — server-wide discovery.** Picks up every project on the GitLab instance carrying a `summarize` or `summarize-team-only` topic, across all groups the token can see, with no group enumeration. GitLab's `?topic=` filter is AND-shaped, so the client issues one `GET /projects?topic=X` per marker and unions by project ID; a project with both topics is fetched once and keeps its full topic list. Same MR-activity gate, same D5 audience classification and same `(team-only)` manifest annotation as `--discover-group`. Composes with `--project` (explicit wins, not marked discovered) and `--discover-group` (union). Bounded by the PAT's visibility — a token that can't see a project won't return it.
- **Activity gate widens to MRs OR issues.** A project whose only window activity is issue updates (a triage week, a planning sprint) was previously dropped from the report before the epic fetch even ran — so an `org::ACME` epic with five closed child issues but no MRs in the window would never reach the customer file. The activity probe now hits `/merge_requests?per_page=1` first (cheap path, hits the common case in one round-trip) and falls through to `/issues?per_page=1` only on the first probe returning empty. Explicitly-listed projects still bypass the gate entirely. 404 on either endpoint still soft-degrades to inactive; 403, 429, 5xx still hard-error.
- **Per-customer epic rollups.** A label of the form `org::CUSTOMER_CODE` on an epic OR on any of its child issues attributes that epic to a customer. The customer-facing epic rollup becomes one file per customer code (`combined--epics-<slug>--<days>d--customer.md`) plus the existing combined file for the unlabelled backlog, so a run with three customers produces three per-customer files plus one combined customer file. The team audience stays one combined file, with both labelled and unlabelled epics included — internal readers want the whole picture. Audience policy (D5) is applied per bucket: a team-only project's epic never lands in any customer file. Multiple `org::` labels on the same epic — whether on the epic itself or distributed across child issues — land in every customer bucket, not just the first. Labels are case-sensitive (`ORG::ACME` is a separate customer). The GitLab epics API already returns `labels` on every epic; `gitlab.Epic` now models the field.
- **Fixed: GitLab publisher's `ensureBranch` POST sent `start_point` (legacy, pre-12.2 field name) instead of `ref`, causing modern GitLab to reject with `400 {"error":"ref is missing, ref is empty"}` on the very first publish of every run.** The struct now uses the modern `ref` JSON tag and the Go field is renamed to match. Regression test `TestGitLabPublisher_EnsureBranchUsesRefField` reads the raw request body and asserts the wire format — not a struct decode — so the test cannot stay in sync by accident.
- **Fixed: the publisher used PUT for every file, including the first publish of a period. GitLab's `PUT /repository/files` rejects a non-existent path with 400 "A file with this name doesn't exist" on older API versions (including the one running at `gitlab.mgmlab.net`); the modern `UpdateService` has a `create_commit!` fallback that auto-creates, but not all self-hosted installs have it. The publisher now uses `POST` for create (when the read returns 404, so `last_commit_id` is empty) and `PUT` for update (when the read returns 200, so `last_commit_id` is round-tripped). The dispatch signal is the same field that already drove the read, so no new state. New test `TestGitLabPublisher_CreateOrUpdateDispatch` asserts GET→POST→GET→PUT order across two consecutive publishes. GitLab's PUT `/repository/files` requires the file's `last_commit_id` (the SHA of the commit that last touched it) for updates; without it, the request looks like an unauthorised concurrent write. The publisher did not track that SHA — it was only fetching the file to read the docbuilder UID, then forgetting the response. The new `readExistingUID` returns both the UID and the SHA; the PUT body now includes `last_commit_id` when the file exists, and omits it (`omitempty`) when the file is new. Two regression tests pin the round-trip and the omission, both reading the raw PUT body so they cannot pass by accident. The struct now uses the modern `ref` JSON tag and the Go field is renamed to match. Regression test `TestGitLabPublisher_EnsureBranchUsesRefField` reads the raw request body and asserts the wire format — not a struct decode — so the test cannot stay in sync by accident.
- **Release pipeline + Docker image.** Releases are cut by GoReleaser on every `v*` tag push (`.github/workflows/release.yml`); cross-platform binaries (linux/darwin/windows on amd64/arm64) ship as tar.gz/zip archives with SHA-256 checksums. Multi-arch Docker images (linux/amd64 + linux/arm64) are built by `docker buildx` and pushed to `ghcr.io/inful/summarizer` with a `-debug` variant for CI use. OCI image metadata (title, description, source, version, created) is set from the goreleaser config so `docker inspect` and registry UIs show the right thing. The `version`, `commit`, and `date` variables in `main` are populated at build time via `-X main.version=...` ldflags — `summarizer version` now prints `summarizer v0.1.1 (commit abc1234, 2026-10-20)` instead of just `summarizer 0.1.0`.
- **Fixed: `--discover-group` alone exited with `at least one --project is required`.** The CLI gate checked only `--project`, contradicting both the README and the pipeline's own gate. The gate now accepts `--project`, `--discover-group` or `--discover-by-topic`.
- **`--period-mode daily|monday`.** Controls the output bucket shape. `daily` (default, v0.1.0 behaviour) gives each cron tick its own `<prefix>/<YYYY-MM-DD>/` directory, branch and MR. `monday` anchors the bucket to the ISO week's Monday, so daily runs across Mon–Sun overwrite the same directory; the GitLab publisher accumulates commits on one branch and reuses the open MR, and the local-disk publisher implies `Force` so the cron doesn't start failing on day 2. Crossing into a new week opens a new bucket. Unknown values fail at parse time (case-sensitive; `weekly` is not accepted — the bucket is a date, not an ISO week number).
- **D5 — GitLab-as-control-plane audience policy** (D5 from `docs/deferred.md`). Three sources of "is this project customer-eligible" union together: the YAML `internal_only_projects:` block, the `--internal-only-project` CLI flag, and the GitLab project's topics (`summarize` for opt-in to customer output; `summarize-team-only` for the override). Discovered projects (via `--discover-group`) default to team-only unless `summarize` is set — the default-safe behavior keeps the customer side bounded even when the operator doesn't know what's in a group.
- **Cross-project epic rollup file** (`combined--epics--<period>--<audience>.md`). Fires whenever ≥1 active epic exists anywhere in the run, independent of project count. Each project's active epics land in dedicated `# Project: …` sections with title, state, web URL, and event count; the LLM synthesizes cross-project themes for both customer and team audiences. One extra LLM call per audience per run.
- **Epic-level rollup in per-project reports.** When a project's GitLab group has epics (Premium/Ultimate feature), the customer and team prompts surface them as `## Epics active this period` with one H3 per epic, linked issues nested underneath, and an `## Other activity` section for events without an epic link.
  - Activity gate: an epic only counts toward the `maxActiveEpics=20` cap when at least one of its linked issues has `updated_at` within the window. Dormant epics (no issue activity this period) are silently dropped — they don't surface in the report and don't burn the cap.
  - Auto-detected project → group mapping via `GET /projects/:id`. Summarizer reads `namespace.kind` and `namespace.full_path` from the project metadata; user-namespace projects (kind=`user`) bypass the `/epics` fetch with no extra config.
  - Graceful degradation: Free-tier GitLab (no `/epics`), wrong group path (404), or auth issues are all detected. 403/404 → empty epic section with a one-line stderr note; 401 → operator-visible error.
- **`--discover-group` flag for activity-based discovery.** Scan a GitLab group's projects, probe each one for activity (a single cheap MR-list call per project with `per_page=1`), and roll the active ones into the run alongside any explicit `--project` listings. Recursion into subgroups is reserved for a future change; v1 ships single-level only. Composable with `--project`; dedupes by project path (explicit listings take precedence on duplicates).
- **Discovery manifest to stderr.** Per-group scan summary with one line per scanned project (included / excluded with reason), plus a one-line totals. Diagnostic — not a separate file.
